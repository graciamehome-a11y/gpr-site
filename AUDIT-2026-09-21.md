# Audit & corrections — 21 septembre 2026

Portée : les 5 points remontés par le client après essai en production
(`https://garage-gracia.vercel.app`), plus un audit complet du projet.

Tout ce qui suit a été **vérifié en direct contre la base de production**
(projet Supabase `gpr-site`, ref `ybnivixfoqaydbwqqbzp`, PostgreSQL 17), pas
déduit de la lecture du code. Les preuves sont indiquées pour chaque constat.

---

## 1. Ce qui bloquait : « connexion impossible avec les vrais emails clients »

### Cause principale — les liens envoyés aux clients pointaient vers `localhost`

| Ce qui a été mesuré | Résultat |
|---|---|
| URL du site configurée dans Supabase | **`http://localhost:3000`** |
| Où aboutissait un lien de réinitialisation | `redirect_to = http://localhost:3000` |

Chaque invitation envoyée à un client lui demandait donc d'ouvrir une page **sur
sa propre machine**, où rien ne tourne. Il ne pouvait jamais définir de mot de
passe, donc jamais se connecter.

### Quatre autres causes, cumulées

2. **Aucune page ne recevait le lien.** Il n'existait ni route `/auth/confirm`,
   ni page « définir mon mot de passe ». Même avec la bonne URL, le lien
   n'aboutissait à rien.
3. **Aucun email ne partait réellement.** Le projet utilise le fournisseur
   d'emails par défaut de Supabase. Sa limite est de **2 emails par heure**, et
   il n'écrit qu'aux membres de l'équipe du projet. Preuve : l'API Management
   refuse toute modification des modèles avec ce message —
   > *« Email template modification is not available for free tier projects
   > using the default email provider. Please upgrade your plan or configure a
   > custom SMTP provider. »*
   Pendant l'audit, un test d'inscription a d'ailleurs reçu en direct
   `email rate limit exceeded`.
4. **Aucun « mot de passe oublié »** n'existait : une personne sans mot de passe
   n'avait aucun recours.
5. **L'inscription libre était ouverte** (`disable_signup: false`) : n'importe
   qui pouvait se créer un compte. Vérifié : un compte a bien été créé pendant le
   test.

### Ce qui a été corrigé

- **Réglages Supabase modifiés** (via l'API Management, sur autorisation) :
  `Site URL` → `https://garage-gracia.vercel.app` ; `Redirect URLs` →
  production + `localhost:3000` ; `disable_signup` → `true`.
  Vérifié après coup : un nouveau lien renvoie désormais vers la production.
- **La création de compte ne dépend plus d'aucun email.** L'admin crée le
  compte, un **mot de passe temporaire s'affiche une seule fois** à l'écran, à
  transmettre de la main à la main. Le compte est utilisable immédiatement.
  C'est aujourd'hui le **seul chemin qui peut fonctionner**, puisque l'envoi
  d'emails est plafonné à 2/heure sur cette offre.
- **Nouveau bouton « Réinitialiser le mot de passe »** sur chaque ligne de la
  page Comptes : il débloque les personnes déjà coincées (invitation jamais
  reçue, mot de passe perdu). La page signale aussi qui ne s'est **jamais
  connecté**.
- **Page « Mon mot de passe »** (icône clé en haut à droite) : chacun peut
  changer son mot de passe.
- **« Mot de passe oublié ? »** sur la page de connexion, avec un message
  honnête : l'envoi restant limité, il vaut mieux demander un mot de passe
  temporaire.
- **Route `/auth/confirm`** : elle reçoit les liens par email et ouvre la
  session. Elle gère les trois formats de lien possibles (jeton, code,
  fragment d'URL), pour fonctionner quelle que soit la configuration future.

### Décision prise : pas d'email pour l'instant

Interrogé sur ce point, le client a choisi de **rester sans envoi d'emails** dans
un premier temps. C'est un choix cohérent : l'application n'en a pas besoin pour
fonctionner, et l'email n'apporterait qu'une chose — que la personne se
débrouille seule en cas d'oubli.

Conséquence appliquée dans le code : **la page « Mot de passe oublié » ne
collecte plus d'adresse email.** Elle expliquait « un email vient de vous être
envoyé » alors que rien ne partait : la personne aurait attendu pour rien, sans
comprendre. Elle décrit maintenant la démarche réelle — demander à un
responsable de générer un mot de passe temporaire depuis la page Comptes.

Le formulaire et son action serveur ont été retirés pour ne pas laisser de code
mort ; ils restent dans l'historique Git si l'on veut les rétablir.

### Si l'on veut activer les emails plus tard

Deux options, par ordre de qualité :

| Option | Coût | Domaine requis | Remarque |
|---|---|---|---|
| **Resend** | 3 000 emails/mois gratuits, 100/jour | Oui | Le plus fiable. Intégration Supabase native. |
| **Brevo** | 300 emails/jour gratuits | Non — validation d'une adresse expéditrice par code | Interface française, mais les envois depuis une adresse `@gmail.com` finissent souvent en indésirables (règles SPF/DMARC de Gmail). |

Un domaine coûte 5 à 10 € par an et améliore les deux : il rend les emails
fiables **et** donne une adresse professionnelle à l'application. C'est le
préalable recommandé.

Marche à suivre une fois le service choisi :

1. Renseigner les identifiants SMTP dans Supabase →
   **Authentication → Emails → SMTP Settings**.
2. Les modèles d'email redeviennent alors modifiables (l'offre gratuite avec
   fournisseur par défaut les verrouille). Le fichier
   `scripts/modeles-email.json` contient les modèles français déjà rédigés,
   pointant vers `/auth/confirm` :
   ```bash
   SUPABASE_ACCESS_TOKEN=sbp_… curl -X PATCH \
     -H "Authorization: Bearer $SUPABASE_ACCESS_TOKEN" \
     -H "Content-Type: application/json" \
     --data-binary @scripts/modeles-email.json \
     https://api.supabase.com/v1/projects/ybnivixfoqaydbwqqbzp/config/auth
   ```
3. Rétablir le formulaire sur `/mot-de-passe-oublie` (voir l'historique Git) :
   la route `/auth/confirm` et la page `/mot-de-passe` sont déjà en place et
   n'ont pas besoin d'être retouchées.

## 2. Faille de sécurité — le solde de carburant était modifiable sans compte

**Constat.** La fonction `ajuster_carburant_stock` est `SECURITY DEFINER` : elle
écrit dans `carburant_stock` en contournant les RLS. Son unique garde-fou était
écrit ainsi :

```sql
if not (mon_role() = 'chef_service_technique' or ...) then raise exception ...
```

Or `mon_role()` renvoie `NULL` dès que la personne n'a pas de ligne dans
`utilisateurs` — ce qui est le cas d'un visiteur non connecté. En SQL,
`NULL = 'x'` vaut `NULL`, donc `NOT (NULL)` vaut `NULL`, et un `IF NULL`
n'exécute pas la branche : **le garde-fou ne se déclenchait jamais.**

**Preuve, avant correction.** Appel de la fonction **sans aucune session**, avec
un site inexistant et un delta nul (donc sans effet sur les données) :

```
insert or update on table "carburant_stock" violates foreign key constraint
```

La fonction avait donc bien été exécutée jusqu'à l'instruction d'écriture. Avec
un identifiant de site réel, n'importe qui muni de la clé anonyme (publique, par
nature) pouvait fixer le solde de carburant de n'importe quel détachement.

**Correction.** Garde-fous réécrits pour toujours renvoyer un booléen strict
(`coalesce(..., false)` et `is not null` explicites), droit d'exécution retiré à
`anon` et à `PUBLIC`, y compris par défaut pour les fonctions futures.

**Preuve, après correction** — le même appel renvoie maintenant :

```
permission denied for function ajuster_carburant_stock   (visiteur anonyme)
Non autorisé                                            (compte connecté sans profil)
```

## 3. Le stock ne diminuait pas

`app/vehicules/actions.ts` insérait la ligne dans `pieces_utilisees` **sans
jamais toucher `stocks`** : l'historique était écrit, le stock non. Aucune
fonction de transfert entre sites n'existait non plus.

**Correction.** Trois fonctions SQL atomiques, plus un journal :

| Fonction | Effet |
|---|---|
| `enregistrer_utilisation` | écrit l'historique **et** décrémente le stock du site du véhicule, en une seule transaction |
| `transferer_stock` | décrémente le site de départ, incrémente celui d'arrivée, journalise les deux |
| `ajuster_stock` | fixe une quantité et journalise l'écart |

La nouvelle table `mouvements_stock` explique chaque variation (qui, quand,
pourquoi). Pour qu'elle soit fiable, **l'écriture directe de `stocks` a été
retirée aux rôles applicatifs** : sans cela, une modification passée par les RLS
n'aurait laissé aucune trace et le journal n'aurait expliqué qu'une partie des
changements.

Décision validée avec le client : **on ne bloque jamais** une déclaration de
réparation. Le stock peut devenir négatif, et s'affiche alors en rouge
« à corriger » — un écart visible vaut mieux qu'une saisie empêchée.

## 5. Autres défauts trouvés et corrigés

- **Fuite d'écran sur appareil partagé (PWA).** Le service worker plaçait
  `/stock`, `/vehicules`, `/bons`… dans un cache **jamais purgé**, alors que la
  déconnexion ne vidait que le cache d'exécution. Sur une tablette de garage
  partagée, la personne suivante pouvait rouvrir hors ligne l'écran de la
  précédente. Le préchargement ne contient plus que la coquille.
- **Mouvement de carburant non atomique.** L'historique était inséré avant la
  mise à jour du solde : en cas d'échec du second appel, un ravitaillement
  apparaissait sans avoir été appliqué. Les deux écritures sont désormais dans
  la même transaction.
- **Course sur le solde carburant.** L'ancien `update … ; if not found then
  insert` faisait échouer deux appels simultanés sur une ligne absente
  (violation d'unicité). Remplacé par `on conflict do update`.
- **Piège `NaN`.** En PostgreSQL, `NaN <= 0` est **faux** et `NaN > 0` est
  **vrai**. Une validation naïve laissait donc passer `NaN`, et
  `quantite + NaN` aurait corrompu un solde **définitivement**. Toutes les
  quantités sont maintenant validées nommément.
- **Site incohérent sur un bon.** Un rôle à vue globale pouvait choisir un
  véhicule de D1 Nikki et déclarer le bon sur D2 Bessassi.
- **Le Chef Garage pouvait ouvrir `/carburant`** et voir un formulaire
  inopérant, alors que le cahier des charges l'en exclut. La page le dit
  désormais explicitement.
- **Erreurs techniques affichées telles quelles.** Les actions serveur
  remontaient le message brut de PostgreSQL. Elles renvoient maintenant un
  message compréhensible, le détail restant dans les journaux serveur.
- **`.env.development.local` pointe vers un stack Supabase local éteint** :
  `npm run dev` échoue en `ECONNREFUSED`. Ce fichier est prioritaire sur
  `.env.local` en développement. Pour travailler sur la vraie base :
  renommer ou supprimer `.env.development.local`, ou relancer le stack local
  (`supabase start`).

## 8. Déploiement — fait le 21 septembre 2026

La migration SQL **et** le code sont en production. Commit `3981d65`.

### Un obstacle inattendu, qui explique bien des choses

Le fichier de liaison Vercel du dépôt (`.vercel/project.json`, non versionné)
pointait vers un projet nommé **`gpr-site`**, appartenant à une équipe à
laquelle le compte Vercel de la machine **n'a pas accès** :

```
Your login is valid, but you can't access the selected team.
```

Or le vrai projet de production s'appelle **`garage-gracia`** et appartient au
compte personnel de l'utilisateur. La liaison était donc périmée : elle
désignait un projet obsolète. Corrigée par `vercel link --project garage-gracia`,
puis `vercel --prod`.

### L'intégration Git n'est pas connectée

C'est la raison pour laquelle **pousser sur GitHub ne déclenche aucun
déploiement**. Vérifié de deux façons : aucun des cinq derniers commits ne porte
de statut de déploiement Vercel sur GitHub, et la commande
`vercel git connect` échoue :

```
Error: Failed to connect graciamehome-a11y/gpr-site to project.
```

Pour la rétablir, il faut autoriser l'application GitHub de Vercel sur le
dépôt (github.com/apps/vercel → *Install* → autoriser `graciamehome-a11y/gpr-site`),
puis relancer :

```bash
npx vercel git connect
```

**En attendant, chaque mise en production se fait à la main** :

```bash
npx vercel --prod
```
